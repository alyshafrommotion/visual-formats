# Matching Chart Format — Implementation SOP

## Reference examples (look here first)

- **Reference examples:** They sit in this same folder, right next to this SOP.

**Whenever this SOP is triggered, open this folder and study the example first** — how the categories are framed, how each maps to a product, and how the reader is meant to find themselves.

## What this format is

A static built as a matching table: the viewer self-selects a category (body type, skin type, hair type, goal, vibe) and reads straight across to the product/variant recommended for them. It works because it does the "which one is right for me?" sorting instantly and flatteringly, and it turns a range into a personalized pick without any branching.

Strongest for **product ranges with clear per-segment fits, "find your match," and problem-aware audiences** choosing among variants.

The one property to protect: **the reader can find the row that's them and land on one clear recommendation** — categories must be self-evident and mutually exclusive.

## Inputs

Expect a **messaging angle**, persona, the **real product range / variants**, and the categories that map cleanly to them. The angle picks the decision; the categories are the rows; this SOP governs the mapping.

## Anatomy

### 1 · The headline (the hook)
- A single "which one are you / what's best for you" question the target wants answered.

### 2 · The category column (self-select)
- A short list of mutually exclusive categories (3–6), each labeled clearly and often with a small icon/illustration so the reader instantly finds themselves.

### 3 · The recommendation column
- Each category maps across to a specific product/variant, ideally with the product shot and a 1-line benefit or name.

### 4 · The CTA
- One clear shop/next-step prompt.

## Build rules (priority order)

1. **Categories must be self-evident and mutually exclusive.** The reader should instantly know which one is them, and only one.
2. **Cover the audience.** The categories together should include everyone you're targeting — no one left without a row.
3. **One clear recommendation per category.** Read straight across; no ambiguity.
4. **Keep it skimmable.** 3–6 rows; legible at thumb size; aligned columns or clean arrows.
5. **Show the product** at each recommendation; add a short benefit or the variant name.
6. **Specificity is credibility.** Real variants, real fits. No absolutes.
7. **One CTA.**
8. **Banned:** overlapping/ambiguous categories, a category with no clear match, tiny unreadable text, "designed to," "seamless."

## Length caps

| Element | Cap |
|---|---|
| Headline | ≤8 words |
| Categories | 3–6 rows |
| Category label | ≤4 words |
| Recommendation | product + ≤6-word benefit/name |
| CTA | 1 |

## Build steps

1. Read the brief: the decision, persona, the variants/endpoints.
2. Write the headline question first.
3. Define 3–6 mutually exclusive categories that cover the audience.
4. Map each category to one product/variant with a short benefit/name.
5. Lay out aligned columns (or arrows) so each row reads across cleanly.
6. Add one CTA.
7. Claims pass (real fits/variants; validate numbers).
8. Design handoff: legible at thumb size, clear category labels/icons, product shots at the recommendations.
9. Deliver: headline, category → recommendation map, CTA, claims flags.

## QA checklist
- [ ] Categories are self-evident and mutually exclusive
- [ ] Categories cover the whole target audience
- [ ] Each category maps to one clear recommendation (read across)
- [ ] 3–6 rows; readable at thumb size
- [ ] Product shown per pick; one CTA
- [ ] Claims validated; no absolutes/banned phrases
