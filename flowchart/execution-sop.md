# Flowchart Format — Implementation SOP

## Reference examples (look here first)

- **Reference examples:** They sit in this same folder, right next to this SOP.

**Whenever this SOP is triggered, open this folder and study the example first** — how the entry question is framed, how the branches split, and how each branch lands on a recommendation.

## What this format is

A static (usually an image) built as a decision tree: an entry question, branching yes/no forks connected by arrows, each branch ending on a product or variant. It works because it turns "which one is right for me?" into a quick, self-directed game that ends on a personalized answer, and the reader does the qualifying themselves.

Strongest for **product ranges with variants, "find your fit," objection-routing (each worry → the answer), and problem-aware audiences** deciding between options.

The one property to protect: **the reader can follow the arrows and land on exactly one recommendation for them.**

## Inputs

Expect a **messaging angle** (the decision being made), persona, the **real product range / variants**, and the qualifying questions that separate them. The angle picks the decision; the variants are the endpoints; this SOP governs the branching.

## Anatomy

### 1 · The entry question (the hook)
- A single question at the top the target instantly wants to answer ("Is this your ___?", "Which ___ are you?").

### 2 · The branches
- 1–3 decision points, each a clean fork (yes/no or a couple of options), connected by arrows. Shallow enough to skim in a few seconds.

### 3 · The terminal nodes (recommendations)
- Each path ends on a specific product/variant, ideally with 2–3 quick benefit bullets and the product shot.

### 4 · The CTA
- One clear shop/next-step button after the recommendation.

## Build rules (priority order)

1. **One entry question that pulls the target in.** It should feel personal ("that's me").
2. **Branches must be mutually exclusive and skimmable.** A reader should never be on two paths at once.
3. **Every path ends on a recommendation.** No dead ends; each fork resolves.
4. **Keep it shallow.** 1–3 decision points; if it needs more, it's too complex for a static.
5. **Arrows do the routing.** Make the flow visually obvious at thumb size.
6. **Benefit, not spec, at the endpoints.** Say what the pick does for them.
7. **Specificity is credibility.** Real variants, real differences. No absolutes.
8. **One CTA at the end.**
9. **Banned:** overlapping branches, dead-end nodes, more than ~3 levels deep, tiny unreadable text, "designed to," "seamless."

## Length caps

| Element | Cap |
|---|---|
| Entry question | ≤8 words |
| Decision points | 1–3 |
| Branch labels | Yes/No or ≤3 words |
| Endpoint bullets | ≤3 per recommendation, ≤6 words each |
| CTA | 1 |

## Build steps

1. Read the brief: the decision, persona, the variants/endpoints.
2. Write the entry question first.
3. Map the qualifying questions that separate the variants; keep to 1–3 forks.
4. Assign each path to a product/variant with 2–3 benefit bullets.
5. Lay out arrows so the flow is skimmable in a few seconds.
6. Add one CTA after the recommendations.
7. Claims pass (real variants/differences; validate numbers).
8. Design handoff: legible at thumb size, obvious arrows, product shots at endpoints.
9. Deliver: entry question, branch map, endpoint recommendations + bullets, CTA, claims flags.

## QA checklist
- [ ] One entry question that feels personal
- [ ] Branches are mutually exclusive and skimmable
- [ ] Every path resolves to a recommendation (no dead ends)
- [ ] ≤3 decision points; readable at thumb size
- [ ] Endpoints lead with benefits; one CTA
- [ ] Claims validated; no absolutes/banned phrases
